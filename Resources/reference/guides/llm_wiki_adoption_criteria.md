# LLM Wiki 채택 기준

이 문서는 `llm-wiki.md`의 일반 아이디어를 StepCode 운영 맥락으로 해석한 **운영 기준 문서**입니다.

목적은 "LLM Wiki 패턴을 이 저장소에서 어디에 채택하고, 어디에는 채택하지 않는가"를 명확히 고정하는 것입니다.

이 문서는 참고 메모가 아니라 운영 판단 기준으로 사용합니다.

---

## 1. 적용 범위

이 기준은 다음 상황에서 사용합니다.

- 새 조사 문서, 비교 문서, 리서치 노트를 어디에 둘지 판단할 때
- LLM이 Markdown 문서를 지속적으로 갱신하는 방식을 도입해도 되는지 판단할 때
- 운영 자산과 보조 지식 자산을 구분할 때
- `llm-wiki.md`의 아이디어를 StepCode에 실제 적용할 수 있는지 검토할 때

이 기준은 다음에는 직접 적용하지 않습니다.

- 웹앱이 직접 읽는 정형 데이터 설계
- 세트/이론/카테고리 인덱스 운영 방식
- 생성 스크립트의 원본/출력 구조 설계

---

## 2. StepCode의 핵심 운영 모델

StepCode의 핵심 운영 모델은 위키가 아니라 **구조화된 콘텐츠 + 생성 스크립트 + 인덱스**입니다.

현재 운영의 중심은 아래 자산입니다.

- `practice/data/content/**`: 사람이 작성하는 운영 원본
- `practice/data/generated/**`: 스크립트가 생성하는 웹용 인덱스/출력
- `practice/data/sets/*.json`: 웹앱이 직접 읽는 문제 세트
- `practice/data/theory/**/*.md`: 웹앱과 이론 인덱스에 연결되는 개념 문서
- `practice/data/categories.json`
- `practice/data/sets.index.json`
- `practice/data/theory.index.json`
- `scripts/new_*`
- `scripts/generate_content_indexes.py`

즉, StepCode는 자유롭게 얽힌 위키보다 **정합성이 중요한 운영 데이터 계층**을 우선합니다.

---

## 3. 채택 원칙

LLM Wiki 패턴은 StepCode에서 **전면 채택하지 않습니다**.

대신 아래 원칙으로 **제한 채택**합니다.

- LLM Wiki는 운영 데이터 계층이 아니라 **보조 지식 계층**으로만 허용합니다.
- 웹앱이 직접 읽는 자산은 기존 생성기와 인덱스 흐름을 우선합니다.
- 자유 서술형 Markdown이 더 적합한 리서치성 자산에만 LLM Wiki 패턴을 허용합니다.
- LLM이 장기적으로 요약, 비교, 링크 정리, 맥락 축적을 맡아도 되는 자산에만 적용합니다.
- 구조화 스키마, ID, 경로 정합성이 핵심인 자산에는 적용하지 않습니다.

한 줄 기준:

> StepCode에서 LLM Wiki는 "서비스를 구동하는 데이터"가 아니라 "운영 판단을 돕는 지식층"에만 사용합니다.

---

## 4. 채택 가능 영역

다음 영역은 LLM Wiki 패턴을 **채택 가능**으로 봅니다.

### 4.1 `Resources/` 계열의 참고 지식 문서

- 외부 자료 조사 문서
- 출제 기준 비교 문서
- 언어별 개념 차이 정리
- 교재/문서/링크 아카이브 요약
- 장기적으로 누적되는 운영 참고 메모

### 4.2 리서치와 분석이 중심인 Markdown 자산

- 여러 소스를 읽고 하나의 비교표나 분석 문서로 엮는 경우
- 질문과 탐색 결과를 문서로 계속 축적하는 경우
- 나중에 사람이 다시 읽고 정책을 정하는 참고 문서를 만드는 경우

### 4.3 중간 지식층으로서의 문서

- 아직 정형 스키마로 넣기 전의 조사 결과
- 커리큘럼 후보 비교
- 도구/워크플로 평가 기록
- 실험 결과 정리 문서

이 경우에도 권장 위치는 루트가 아니라 `Resources/reference/` 계열입니다.

---

## 5. 비채택 영역

다음 영역은 LLM Wiki 패턴을 **채택하지 않습니다**.

### 5.1 웹앱이 직접 읽는 운영 데이터

- `practice/data/categories.json`
- `practice/data/sets.index.json`
- `practice/data/theory.index.json`
- `practice/data/sets/*.json`
- `practice/data/generated/**`

이 자산들은 정형 필드, 경로, ID 정합성이 핵심이므로 자유형 위키 편집 방식과 맞지 않습니다.

### 5.2 생성 스크립트 기반 운영 원본

- `practice/data/content/**`
- `scripts/new_content_category.py`
- `scripts/new_lesson.py`
- `scripts/new_worksheet.py`
- `scripts/generate_content_indexes.py`

이 영역은 이미 생성기 중심의 단일 흐름이 있으므로, 위키식 누적 편집보다 **명시적 스키마와 생성 절차**를 유지해야 합니다.

### 5.3 런타임 자산과 직접 연결된 문서

- 이론 인덱스에 직접 연결되는 운영 문서
- 경로가 바뀌면 웹 동작이 깨지는 문서
- 자동화 스크립트가 직접 참조하는 파일

이 자산은 사람이 의도적으로 통제해야 하며, LLM의 자유로운 교차 업데이트 대상이 아닙니다.

---

## 6. 실무 판단 체크리스트

아래 질문으로 채택 여부를 판단합니다.

### 6.1 채택 가능 판단

다음 5개 중 4개 이상이 `예`면 채택 가능으로 봅니다.

1. 이 문서는 LLM이 지속적으로 갱신해도 되는가
2. 자유 서술형 Markdown이 구조화 JSON보다 더 적합한가
3. 여러 출처를 엮은 요약, 비교, 맥락 축적이 핵심인가
4. 문서가 깨져도 웹앱 런타임에 직접 영향이 없는가
5. 최종 운영 데이터가 아니라 참고용 중간 지식층인가

### 6.2 비채택 판단

다음 중 하나라도 `예`면 비채택이 안전합니다.

1. 웹앱이 직접 읽는가
2. ID, 파일 경로, 인덱스 정합성이 중요한가
3. 생성기나 검증 스크립트가 이미 있는가
4. 사람이 최종값을 명시적으로 통제해야 하는가

---

## 7. 권장 저장 위치와 운영 방식

LLM Wiki 패턴을 제한 채택하는 경우 권장 방식은 다음과 같습니다.

### 7.1 저장 위치

- 운영 기준/참고 문서: `Resources/reference/guides/`
- 주제별 조사 문서: `Resources/reference/` 하위 적절한 폴더
- 단기 실험 메모: `Projects/active/<YYYYMMDD_slug>/`

루트에는 일반적으로 두지 않습니다.

### 7.2 운영 방식

- 원문 자료는 별도 보관하고, LLM은 요약/비교/연결 문서만 관리합니다.
- 조사 문서는 자유형 Markdown으로 누적해도 되지만, 운영 데이터로 승격할 때는 기존 생성 흐름으로 옮깁니다.
- LLM이 만든 분석 결과를 바로 `practice/data/**`에 반영하지 않고, 사람이 검토 후 구조화합니다.
- 위키식 문서는 "참고용 지식층"으로 유지하고, 서비스 구동 데이터와 혼합하지 않습니다.

---

## 8. 결론

StepCode에서 `llm-wiki.md`의 아이디어는 **부분 채택**이 적절합니다.

- `Resources/` 계열의 조사/비교/리서치 문서에는 유용합니다.
- `practice/data/**`와 생성 스크립트 중심 운영 계층에는 부적합합니다.

따라서 이 저장소에서 LLM Wiki는 전면 운영 모델이 아니라, **운영 판단을 지원하는 보조 지식 시스템**으로만 사용합니다.
