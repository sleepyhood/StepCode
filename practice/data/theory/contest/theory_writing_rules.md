# 경시 이론 문서 작성 규칙 (Contest Theory Rules)

## 1) 목적
- 이 문서는 주차별 이론 문서를 작성할 때의 공통 규칙입니다.
- 목표는 "현재 문제 정답 맞히기"가 아니라 "유형 전이(응용) 가능성"을 만드는 것입니다.

## 2) 현재 문제점
- 이론이 특정 문제 정답으로 바로 연결되는 문장 위주로 작성되는 경향이 있습니다.
- 예시가 실제 문제와 거의 동일해서 학생이 응용하기 어렵습니다.
- 결과적으로 "암기형 풀이"가 되고, 변형 문항 대응력이 떨어집니다.

## 3) 핵심 원칙
1. 이론은 문제보다 넓어야 한다.
- 한 문제에만 통하는 규칙이 아니라, 같은 유형 전체에 적용 가능한 규칙을 설명한다.

2. 예시는 유사 예시를 사용한다.
- 실제 문제 코드/숫자/문구를 그대로 재사용하지 않는다.
- 같은 개념의 유사 패턴으로 예시를 만든다.

3. 해설은 정답 유출형이 아니어야 한다.
- "최종 출력은 X"만 쓰지 않는다.
- 판별 기준, 추적 절차, 오답 포인트를 먼저 제시한다.

4. 문제-이론 연결은 하되, 문제 복제는 하지 않는다.
- "어떤 개념이 연결되는지"만 표기하고, 문제 본문 재현은 금지한다.

5. 주차 분리를 지킨다.
- W01과 W10처럼 주제가 겹치면, W01은 진단 수준 요약만 두고 상세는 해당 주차(W10)에 둔다.

## 4) 예시 작성 규칙
1. 금지
- 실제 기출의 숫자/문자열/선지를 그대로 사용
- 실제 문제 코드와 동일한 코드 블록 사용
- 문제 정답을 직접 유도하는 문장 ("그래서 정답은 ③")
- 예시 라벨에 금지 키워드를 사용하는 표현

2. 권장
- 구조는 같고 값은 다른 "유사 예시" 사용
- 1개 정예 예시 + 1개 변형 예시 제공
- 경계값/함정값 예시를 추가
- 예시 라벨은 `예시 (기본)`, `예시 (변형)`, `예시 (함정)`처럼 단순하게 표기
- 예시마다 `입력`(해당 시)과 `출력`을 함께 표기

3. 예시 최소 구성
- 기본 예시 1개
- 변형 예시 1개
- 오답 유도 예시 1개
- 각 예시는 결과 확인이 가능하도록 출력값을 반드시 포함
- 입력이 필요한 예시는 입력값도 반드시 함께 포함

## 5) 설명 구조 규칙
모든 핵심 개념은 아래 순서로 작성한다.
1. 개념 정의: 무엇을 판단하는가
2. 판별 규칙: 무엇을 보면 되는가
3. 추적 절차: 어떤 순서로 계산/판단하는가
4. 오답 포인트: 어디서 틀리는가
5. 유사 예시: 문제와 직접 동일하지 않은 관련 예시

## 6) 어체 규칙
1. 기본 어체
- 설명/안내/정의 문장은 `~입니다.`로 끝낸다.

2. 예외 어체
- 규칙/루틴/체크리스트/판별 프레임은 `~다.`로 끝낸다.

3. 금지 어체
- 같은 섹션 안에서 `~다.`와 `~입니다.`를 무작위로 섞지 않는다.

## 7) 문제/정답 문서와의 관계
1. theory 문서
- 개념, 규칙, 절차, 실수 패턴 중심

2. problem 문서
- 실제 문항 원문 중심

3. answer 문서
- 정답 + 해설 메모 중심
- 해설 메모도 정답 직접 유도 문장을 최소화한다.

## 8) 품질 체크리스트 (작성 후 필수)
1. 이론 예시가 실제 문제와 동일하지 않은가
2. 개념이 최소 2개 이상의 변형 문항에 적용 가능한가
3. 정답 번호/값을 직접 노출하는 설명이 과도하지 않은가
4. 오답 포인트가 명시되어 있는가
5. 어체가 규칙에 맞게 통일되었는가
6. 다른 주차와 주제 중복이 없는가

## 9) 권장 템플릿
```md
## 공통 이론 (COMMON)
### 1) 개념명
- 개념 정의: ...입니다.
- 판별 규칙: ...다.
- 추적 절차: ...다.
- 오답 포인트: ...입니다.

예시 (기본):
```python
# 실제 문제와 값/문구가 다른 유사 코드
```
```io
input:
(없음)
output:
...
```

예시 (변형):
```python
# 경계값/함정 포함
```
입력이 필요한 경우:
```io
input:
...
output:
...
```
```

## 10) 운영 규칙
- 기존 이론 문서를 고칠 때도 이 규칙을 우선 적용한다.
- 기출 원문이 바뀌어도 theory는 "개념 중심"을 유지한다.
- 문제 교체 시 theory는 예시 숫자/맥락만 조정하고 구조는 유지한다.
- 각 주차 이론은 해당 주차 `problem`/`answer`를 풀 수 있는 최소 개념을 반드시 포함한다.
- 개념 누락 점검 시, 문항별로 `필요 개념 -> 이론 섹션` 역매핑이 가능해야 한다.

## 11) SVG 작성 규칙
1. 목적 규칙
- SVG 1개는 개념 1개만 설명한다.

2. 제목 규칙
- 이미지 내부 좌상단 헤더(큰 제목)는 넣지 않는다.
- 문서 제목/섹션 제목과 중복되는 제목 텍스트를 넣지 않는다.

3. 언어 규칙
- 설명 문구는 한국어로 통일한다.
- 코드/수식/함수명은 원문 표기를 허용한다.

4. 폰트 규칙
- 기본 폰트 스택은 아래로 고정한다.
- `"Pretendard", "Noto Sans KR", "Malgun Gothic", "Apple SD Gothic Neo", sans-serif`

5. 크기 규칙
- 기본 캔버스는 가로형을 사용한다.
- 일반 다이어그램은 `980x320`, 흐름/격자형은 `980x360`을 기본으로 한다.

6. 색상 규칙
- 의미별 색을 고정해 재사용한다.
- 기본 텍스트/선, 강조(파랑), 경고/제외(빨강), 배경 박스(연회색) 체계를 유지한다.

7. 표기 규칙
- 출력 공백을 설명할 때는 `_`로 표기한다.
- 기호/색 의미가 있는 경우 범례를 함께 제공한다.

8. 난이도 규칙
- SVG는 특정 문항 정답을 직접 노출하지 않는다.
- 문제 직접 복제 대신 범용 예시 구조를 사용한다.

9. 접근성 규칙
- 문서 삽입 시 alt 텍스트를 반드시 작성한다.
- alt 텍스트는 "무엇을 보여주는 그림인지"를 한 줄로 명시한다.

10. 파일명 규칙
- 파일명은 `contest_wNN_topic_key.svg` 패턴으로 작성한다.
- 소문자/언더스코어 기반으로 통일한다.

11. 배치 규칙
- 각 개념 설명 직후, 첫 코드 예시 전에 SVG를 배치한다.
- 같은 개념 안에서 SVG를 여러 개 쓸 경우 핵심 그림 1개를 먼저 배치한다.

12. 검수 규칙
- 삽입 전 아래 3가지를 점검한다.
- 한글 깨짐이 없는가.
- 모바일 폭에서 텍스트/도형 겹침이 없는가.
- 문서 링크 경로가 정상 동작하는가.
