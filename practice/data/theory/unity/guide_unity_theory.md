# Unity Theory 작성 가이드

## 목적
1. 학생이 이론 문서만 읽고도 대응 문항을 풀 수 있어야 한다.
2. 이미지 자료는 설명 보조가 아니라 오답 방지 근거로 사용한다.
3. 제작 메타(문항 매핑)는 유지하되 학생 화면에는 노출하지 않는다.
4. 특정 문항 암기보다 변형 문항 대응력(유형 전이)을 우선한다.

## 적용 범위
1. 대상: `practice/data/theory/theory_unity_*.md`
2. 인덱스: `practice/data/theory.index.json`
3. 이미지 폴더: `practice/data/theory/images`

## 필수 구조
1. `# 제목`
2. `## 학습 목표` (2~4개)
3. `## 범위` (키워드 중심, 학생에게 불필요한 번호 노출 금지)
4. `## 핵심 패턴` (코드 1개 이상)
5. `## 문항 핵심 포인트` (출제 의도별 묶음)
6. `## 자주 하는 실수`
7. `## 빠른 체크리스트`
8. `## 미니 체크` (최소 3문항)
9. `## 연결 세트`

## 문항 커버 규칙 (가장 중요)
1. 범위에 적은 문항 번호는 본문에서 실제로 설명되어야 한다.
2. 각 문항은 아래 3요소를 모두 커버해야 한다.
   - 개념 정의
   - 오답 포인트
   - 정답 판별 기준
3. 참/거짓 문항이 있으면 본문에 참/거짓 판단 근거를 명시한다.
4. API/식별자/이벤트 함수는 대소문자 정확 표기를 반드시 포함한다.
5. 단순 정의 나열 금지: 최소 1개 코드 또는 실제 UI 맥락을 함께 제시한다.

## 개념 설계 원칙 (유형 전이)
1. 이론은 특정 문항 1개보다 넓어야 한다.
2. 문항 연결은 유지하되, 문제 본문/선지/숫자/문구를 그대로 복제하지 않는다.
3. 예시는 구조는 같고 값/맥락은 다른 "유사 예시"를 사용한다.
4. 개념 설명 기본 흐름은 `개념 -> 오답 포인트 -> 판별 기준 -> 유사 예시`를 권장한다.

## 학습 몰입도 및 텍스트 체류 시간 강화
1. **표면적 기능 이상의 원리 제시**: 단순히 "무엇을 한다"를 넘어, 그 기능이 작동하는 엔진 내부의 원리(예: 직렬화, 최적화 구조 등)를 최소 1개 이상 포함한다.
2. **실무적 워크플로우 팁**: 교과서적인 설명 외에도 실제 개발자들이 사용하는 도구 활용법(예: Debug 모드, 창 고정 등)을 '꿀팁' 형태로 제공하여 흥미를 유발한다.
3. **시각적 변화와 피드백 강조**: 코드를 고쳤을 때나 옵션을 바꿨을 때 에디터 화면(인스펙터의 선 굵기 변화, 색상 변화 등)에서 일어나는 시각적 피드백을 상세히 묘사한다.
4. **시나리오 중심의 깊이**: 질문의 폭을 "A는 무엇인가?"에서 "성능 최적화가 필요한 이 상황에서 왜 A 옵션을 선택해야 하는가?"로 확장하여 사고를 유도한다.

## 예시 작성 규칙 (Unity)
1. 금지:
   - 원문 문제 코드/수치/문구를 그대로 재사용
   - "그래서 정답은 n번" 같은 정답 유출형 설명
2. 권장:
   - `예시 (기본)`, `예시 (변형)`, `예시 (함정)` 3종
   - Unity 실행 맥락(Inspector/Console/Component 참조) 포함
3. 최소 구성:
   - 기본 1개 + 변형 1개 + 함정 1개

## 주차 운영 규칙 (문제/정답 분리)
1. 주차별 학습 자료는 아래 3개 문서를 1세트로 운영한다.
   - `problem_unity_wNN.md`: 학생용 문제지
   - `answer_unity_wNN.md`: 교사용 정답/해설
   - `problem_unity_wNN_map.md`: 원문 번호 + 추가 문제 출처/의도 매핑
2. 한 주차의 문제 구성은 "원문 대응 + 확장 문제"를 함께 둔다.
3. 권장 비율:
   - 원문 대응 문제 60~80%
   - 확장(변형/함정/응용) 문제 20~40%
4. 주차 문서 생성 후 JSON 세트로 변환한다.
5. 역매핑이 가능해야 한다: `문항 -> 필요 개념 -> 이론 섹션 -> 세트 ID`

## 학생 노출 규칙
1. 본문에 `n번`, `문항 번호`, 제작 메모를 직접 노출하지 않는다.
2. HTML 주석(`<!-- ... -->`)에 제작 메모를 넣지 않는다.
3. 학생 화면에는 학습 내용만 남긴다.

## 제작 메타 규칙 (번호 보존)
1. 문항 매핑은 `theory.index.json`에 저장한다.
2. Unity 항목에 아래 필드를 사용한다.
   - `sourceProblemIds`: 문항 번호 배열
   - `sourceSectionMap`: 섹션명 -> 문항 번호
3. 문서 수정 시 매핑 변경이 있으면 인덱스도 함께 갱신한다.

## 이미지 규칙
1. 이미지는 "없으면 오해가 생기는 지점"에만 넣는다.
2. 이미지 1개마다 반드시 아래 2줄을 붙인다.
   - 이미지 마크다운
   - 캡션 + 출처 링크
3. 캡션 형식:
   - `*캡션: ... 출처: [문서명](URL)*`
4. 파일명 규칙:
   - `unity_uXX_topic_purpose.ext`
   - 예: `unity_u02_log_operator_console.png`
5. 저장 위치:
   - `practice/data/theory/images`
6. 경로 표기:
   - `./data/theory/images/<file>`
7. 권장 소스 우선순위:
   - Unity Manual / Unity Scripting API / Microsoft C# docs
8. 출처 링크는 이미지 원본 또는 해당 공식 문서 페이지 중 하나를 반드시 포함한다.

## 이미지 배치 기준
1. UI 개념(Inspector, Console, Scene Tool): 해당 설명 직후 배치
2. 연산/문법 개념: 코드 패턴 직후 배치
3. 명명 규칙/오타 방지: 올바른 표기 vs 틀린 표기 설명 바로 아래 배치
4. 한 섹션에 이미지가 2개를 넘으면 학습 흐름이 끊기는지 점검한다.

## 스타일/표현 규칙
1. 문장은 짧게, 판단 기준은 명확히 쓴다.
2. "왜 틀리는지"를 먼저 쓰고 "어떻게 고치는지"를 붙인다.
3. 예시는 바로 실행 가능한 C# 문법으로 제시한다.
4. "항상/절대" 표현은 예외가 없을 때만 사용한다.
5. 플랫폼/버전 의존 UI 경로는 변형 경로를 함께 표기한다.

## 개념 수 가드레일
1. 주차(유닛)당 권장 핵심 개념 수는 4~6개다.
2. 기본 허용 범위는 3~7개다.
3. 진단/총정리 성격 유닛은 예외 허용 가능하며, 문서에 근거 1줄을 남긴다.

## 문서 역할 분리
1. theory 문서: 개념/규칙/오답 패턴 중심
2. problem 문서: 실제 문항 원문 중심
3. answer 문서: 정답 + 해설 메모 중심

## 품질 체크리스트 (출고 전)
1. 범위에 적은 문항이 모두 본문에 실제 반영됐는가?
2. 각 핵심 포인트에 정답 판별 근거가 있는가?
3. 이미지마다 캡션/출처가 붙어 있는가?
4. 이미지 경로가 `./data/theory/images/...`로 올바른가?
5. 본문에 문항 번호/제작 메모가 노출되지 않는가?
6. `theory.index.json`의 `sourceProblemIds`/`sourceSectionMap`이 최신인가?
7. 미니 체크 문항이 실제 핵심 포인트를 검증하는가?
