# Pygame 문제 제작 운영원칙

이 문서는 `pygame` 회차형 문제지를 제작할 때
공통으로 적용하는 최종 운영 규칙이다.

적용 대상:

- `round01`
- 이후 추가되는 모든 `roundNN`

이 문서는 세부 정답 문서가 아니다.
회차별 문제를 만들 때 반복해서 확인해야 하는
설계, 검수, 자동채점 기준만 남긴다.

---

## 1. 최종 운영 규칙

### 1.1 문제 구조

- 기본 단위는 `대문항 중심`으로 설계한다.
- 대문항 수는 `6개 내외`를 기본으로 한다.
- 각 대문항은 `하나의 실행 맥락`을 가진다.
- 소문항은 같은 코드 안에서 단계적으로 이어지게 한다.
- 소문항 풀이 방식은 `누적풀이`를 기본으로 강제한다.
- 앞 소문항을 해결하지 못하면 뒤 소문항 풀이가 자연스럽게 막히는 구조를 허용한다.
- 따라서 각 소문항은 이전 소문항의 수정 상태를 이어받는다는 점을 문서에서 일관되게 유지해야 한다.

### 1.2 학생 제공 방식

- 학생에게는 `문제 파일`을 직접 제공하지 않는다.
- 학생은 문제지에 제시된 코드를 `직접 입력`하고 실행한다.
- 체류시간은 문항 수보다 `입력 -> 실행 -> 관찰 -> 판단` 단계로 확보한다.

### 1.3 검수 기준 문서

- 회차별 검수 원본은 `MD`를 마스터로 사용한다.
- 검수 문서에는 `문제`, `정답`, `해설`, `부분 정답 기준`, `실행 확인 결과`가 함께 있어야 한다.
- 검수 문서에는 반드시 `제시 코드`가 포함되어야 한다.
- 실제 실행용 `problem*.py`는 별도로 유지하고, 검수 문서와 동기화한다.
- 모든 소문항은 같은 메타 구조를 따라야 한다.
- `x.4` 같은 후반 소문항도 예외 없이 메타를 모두 갖춰야 한다.

### 1.4 문항 형식 우선순위

- `빈칸형`을 우선한다.
- `복수정답 객관식형`을 다음 우선순위로 둔다.
- `코드 입력형`은 필요한 최소한으로만 사용한다.
- `자유서술형`과 `자연어 정답형`은 사용하지 않는다.

### 1.5 코드 입력형 축소 기준

- 정답이 `2줄 이상`이면 우선 빈칸형 또는 선택형 전환을 검토한다.
- 한 줄이라도 인수나 조건 조합이 많으면 빈칸형 전환을 검토한다.
- 자동채점 기준이 흔들리는 코드 입력형은 유지하지 않는다.

### 1.6 블록 교체형 문항

- 블록 교체형 문항은 `BLOCK_A_START`, `BLOCK_A_END` 같은 마커를 사용한다.
- 줄 번호를 기준으로 문항을 설계하지 않는다.
- 블록 교체형 문항은 `교체 -> 실행 -> 결과 판단` 구조를 기본으로 한다.
- 제시 코드 안의 주석 번호와 검수 문서의 문항 번호는 반드시 일치해야 한다.
- 코드 주석 번호가 실제 문항 번호와 다르면 배포 전 수정한다.

### 1.7 이미지와 GIF

- 참고 자료는 `대문항 단위`로만 붙이는 것을 기본으로 한다.
- 참고 자료는 `오류 상태`가 아니라 `정상 작동 상태`를 기준으로 만든다.
- 정지 화면으로 충분한 문제는 `PNG`를 사용한다.
- 움직임이나 입력 반응이 핵심인 문제만 `GIF`를 검토한다.
- GIF가 과하면 `연속 캡처 2~3장`으로 대체한다.

### 1.8 자동채점 원칙

- 정답은 가능한 한 `하나로 고정`되게 만든다.
- 함수명, 상수, 숫자, 좌표, 코드 조각, 선택 조합 중심으로 설계한다.
- 채점 로직이 복잡해지는 문항은 문항 구조를 먼저 바꾼다.
- 미동기화된 문항은 임시 상태로 두지 않는다.
- `이후 보완`, `동기화 필요` 상태의 문항은 검수 완료 상태로 간주하지 않는다.
- 실제 코드, 문항 설명, 정답, 실행 결과가 모두 일치해야만 확정 문항으로 본다.

### 1.9 JSON 변환 원칙

- `MD 검수 확정 -> JSON 변환` 순서를 지킨다.
- 가능한 한 기존 `json_schema_guide.md`를 따른다.
- 현재 가이드와 충돌하는 대표 유형은 `복수정답 객관식형`이다.
- 필요 시 `mcq_multi` 같은 확장 타입을 별도로 검토한다.

## 2. 시행착오에서 확정된 교훈

- 문제를 잘게 많이 쪼개면 제작, 검수, 웹 반영 비용이 같이 커진다.
- JSON은 구조화에 강하지만, 1차 검수 원본으로는 MD보다 불리하다.
- 자연어 정답은 자동채점 비용이 너무 크다.
- 긴 코드 입력형은 채점과 유지보수 모두 불안정하다.
- 제시 코드와 실행 코드는 분리되어 있어야 관리가 된다.
- 동적 문제는 정지 이미지보다 GIF 또는 연속 캡처가 효과적일 수 있다.

## 3. 회차별 체크리스트

### 3.1 구조

- 대문항 수가 과도하지 않은가
- 각 대문항이 하나의 실행 맥락을 가지는가
- 소문항 흐름이 단계적으로 이어지는가
- 소문항이 누적풀이 구조로 읽히는가
- 뒤 문항의 전제가 앞 문항 수정 결과와 모순되지 않는가

### 3.2 정답 구조

- 자유서술형이 남아 있지 않은가
- 2줄 이상 코드 입력형이 남아 있지 않은가
- 빈칸형이나 선택형으로 더 줄일 수 없는가
- 모든 소문항에 메타 항목이 빠짐없이 들어갔는가

### 3.3 시각 자료

- 필요한 대문항에만 참고 자료가 들어갔는가
- 참고 자료가 정상 작동 상태 기준인가
- GIF 사용이 정말 필요한가

### 3.4 동기화

- 검수 문서와 `problem*.py`가 일치하는가
- 이미지와 문항 설명이 일치하는가
- 이후 JSON으로 옮길 때 타입과 정답 구조가 맞는가
- 제시 코드 주석 번호와 실제 문항 번호가 일치하는가
- `동기화 필요` 상태로 남아 있는 문항이 없는가
