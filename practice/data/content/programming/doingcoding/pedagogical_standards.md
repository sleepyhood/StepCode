# StepCode — 교육적 품질 표준 (Pedagogical Standards)

이 문서는 StepCode의 문제 콘텐츠가 **"선생님 없이도 학생이 혼자 이해할 수 있는 수준"**인지 검증하는 표준을 정의합니다.
문제를 만드는 사람은 답을 알기 때문에 논리적 비약을 인지하지 못합니다. 이를 **전문가의 저주(Expert Blindness)**라고 합니다.
이 문서는 그 저주를 방지하기 위한 체계적인 감사(Audit) 프롬프트와 개선(Improvement) 프롬프트를 제공합니다.

> **적용 대상**: `content_production_pipeline.md`의 **Phase 6: 교육 품질 검토** 단계.

---

## 1. 5성급 품질 기준 (5-Star Standard)

모든 문제는 게시 전 아래 5가지 기준을 충족해야 합니다.

| 번호 | 기준 | 체크 포인트 | 실패 신호 |
|:---:|:---|:---|:---|
| ⭐1 | **전략적 시각 자료** | 새로운 개념의 도입부이거나, 기하학적 로직 등 '그림'이 없으면 이해가 5분 이상 지체되는가? | 입문용 튜토리얼이나 도형 문제임에도 시각 자료가 전혀 없다 |
| ⭐2 | **예제 추적** | "왜 이 입력이 이 출력이 되는지" 컴퓨터의 사고 과정을 한 단계씩 보여주는가? | 예제 입출력이 있지만 왜 그런지 설명이 없다 |
| ⭐3 | **개념 중립성** | 특정 언어 문법이 아닌 알고리즘 로직 자체를 설명하는가? | C 코드 이미지만 있고, Python/Java 학생은 소외된다 |
| ⭐4 | **점진적 힌트** | 힌트가 "정답 코드 스포"가 아닌 "사고 방향 유도"로 구성되어 있는가? | `has_hint: false`이거나 힌트가 코드를 그대로 보여준다 |
| ⭐5 | **전략적 예제** | 단순 수치 나열이 아닌, '원리 이해용'과 '함정 돌파용(반례)' 예제가 골고루 섞여 있는가? | 예제가 너무 단순하여 문제의 특이 케이스를 설명하지 못한다 |
| ⭐6 | **단일 페르소나** | 문서 전체가 한 명의 강사가 설명하는 것처럼 일관된 어조를 유지하는가? | 기존의 구어체 설명 뒤에 갑자기 딱딱한 AI 표가 등장한다. |

## 2. 감사 프롬프트 모음 (Audit Prompts)

문제 본문을 AI에게 붙여넣고, 아래 프롬프트를 함께 사용합니다.

---

### 🔍 Prompt A — 초보자 페르소나 감사 (가장 중요)
> **용도**: 전문가의 저주를 깨고, 학생이 어디서 막히는지 파악.

```
[ROLE] 너는 이제 막 반복문을 배운 14세 입문자야. **너는 모르는 단어가 나오면 금방 의욕을 잃고, 설명이 3줄 이상 길어지면 읽기를 포기해.** 특히 '추상적인 개념'을 들으면 머릿속이 하얘지는 특징이 있어.

[TASK] 아래 문제를 읽고, 다음 3가지를 각각 솔직하게 답해줘.
1. "이게 무슨 소리야?"라고 느낀 문장이나 표현 (최대 3개)
2. 예제 입출력을 보고도 왜 그 답이 나오는지 모르겠는 부분
3. 이 문제를 혼자 풀다가 포기할 것 같은 순간은 언제인가?

[FORMAT] 각 항목을 번호 목록으로 출력. 감싸는 맥락 설명 없이 바로 시작.
```

---

### 🔍 Prompt B — 언어 중립성 감사
> **용도**: C 코드 이미지나 특정 언어 문법에 의존하는 부분 발견.

```
[ROLE] 너는 Python만 배운 대학교 1학년 학생이야. C언어를 전혀 모른다.

[TASK] 아래 문제를 읽고, 이것이 Python으로 풀 수 있는 문제인지 판단해줘.
1. 문제 설명에서 C언어를 모르면 이해할 수 없는 부분을 지적해줘.
2. 핵심 알고리즘(재귀)의 개념이 언어와 무관하게 설명되어 있는가?
3. 개선을 위해 추가해야 할 언어 중립적 설명을 제안해줘.
```

---

### 🔍 Prompt C — 힌트 품질 감사
> **용도**: 힌트가 너무 직접적이거나 없는 경우 탐지.

```
[ROLE] 너는 교육학을 전공하는 대학원생이야. 스캐폴딩(Scaffolding) 이론에 정통하다.

[TASK] 이 문제의 힌트(없는 경우 문제 본문의 설명)가 적절한 스캐폴딩을 제공하는지 평가해줘.

[CRITERIA] 좋은 힌트는 다음 3단계를 순서대로 유도한다.
  Step 1. "무엇을 먼저 생각해야 하나?" (방향 제시)
  Step 2. "어떤 전략으로 접근하나?" (접근법 암시)
  Step 3. "구체적으로 어떻게 구현하나?" (부분 로직, 코드 아님)

현재 힌트가 어느 단계에서 실패하는지, 그리고 개선안을 제시해줘.
```

## 3. 개선 프롬프트 모음 (Improvement Prompts)

감사 결과를 바탕으로 본문을 수정할 때 사용합니다.

---

### 🛠️ Prompt D — 예제 추적 섹션 추가
> **용도**: "왜 이 입력이 이 출력이 되는지" 컴퓨터의 사고 과정 추가.

```
[TASK] 아래 문제의 예제 입출력 1번에 대해 "컴퓨터의 생각 과정(Trace)"을 작성하되, 기존 본문에 있는 중복되는 설명이나 텍스트를 삭제하고 하나로 통합해줘. 

[PLACEMENT]
- 기본적으로 `## 4. 힌트`의 가장 첫 번째 항목(힌트 1)으로 배치해.
- 만약 문제 이해를 위해 필수적인 과정이라면 `## 1. 문제 설명`의 가장 하단에 배치해.

[FORMAT]
- `### 🖥️ 예제 1 추적 (N=10일 때 어떻게 동작하는가?)` (반드시 H3 사용)
- 형식: 재귀 호출 트리 또는 단계별 표
- 각 단계에서 함수가 무엇을 하는지 한국어로 설명
- 최종 출력이 왜 그렇게 나오는지 결론으로 마무리

[CONSTRAINT]
- 기존의 조잡한 구어체와 AI의 정제된 문체가 섞이지 않도록 전체 문맥을 자연스럽게 다듬을 것.
- **절대 새로운 `##` (H2) 헤더를 생성하지 마.** 기존 1~4번 구조를 유지해야 해.
- 정답 코드를 직접 보여주지 말 것.
- 학생이 "아, 그렇구나!"를 느끼는 순간이 포함되어야 함.
```

---

### 🛠️ Prompt E — Mermaid 시각화 추가
> **용도**: 공간/트리 구조가 핵심인 문제에 다이어그램 삽입.

```
[TASK] 아래 문제의 핵심 알고리즘을 Mermaid 다이어그램으로 시각화해줘.

[TYPE] 다음 중 해당하는 타입을 선택:
  - "graph TD" : 재귀 호출 트리 (어떤 함수가 어떤 함수를 부르는가)
  - "sequenceDiagram" : 실행 순서 (호출과 반환의 흐름)
  - "flowchart" : 알고리즘의 조건 분기

[CONSTRAINT]
- 다이어그램 삽입 전, 이 그림이 무엇을 의미하는지 설명하는 브릿지 문장을 반드시 작성하여 본문과의 흐름을 연결할 것.
- 노드 레이블은 한국어로, 변수값은 구체적인 숫자 예시를 사용
- 5개 이하의 노드로 단순하게 핵심만 표현
- 학생이 코드를 읽기 전에 이 다이어그램만 보고도 로직이 직관적으로 이해되어야 함
```

---

### 🛠️ Prompt F — 점진적 힌트 재작성
> **용도**: 없거나 부실한 힌트를 3단계 스캐폴딩으로 교체.

```
[TASK] 아래 문제의 난이도와 핵심 개념을 분석하여 힌트의 필요성을 판단하고 재작성해줘.
	1. **난이도 하 (단순 변형/연습)**: 힌트를 작성하지 않거나, "이전 문제와 어떤 점이 다른지 생각해보세요" 정도의 **한 줄 팁**만 제공할 것.
	2. **난이도 중/상 (개념 도입/복잡한 로직)**: 기존 가이드의 **3단계 점진적 힌트**를 적용하여 재구성할 것.

[FORMAT]
### 💡 힌트 1 (방향) — 무엇을 먼저 생각해야 하나?
(정답을 절대 암시하지 않고, 문제를 '어떻게 바라볼지'만 유도)

### 💡 힌트 2 (전략) — 어떤 방식으로 접근하나?
(재귀? 반복? 수학? 접근 방식만 제안. 코드 구조 암시 가능)

### 💡 힌트 3 (구현 방향) — 코드로 어떻게 옮기나?
(함수 시그니처나 핵심 조건문 패턴을 의사코드(Pseudocode)로 제시. 완성 코드 금지)

[CONSTRAINT]
- 힌트가 불필요하다고 판단되면 `## 4. 힌트` 섹션에 "(이 문제는 스스로의 힘으로 충분히 해결할 수 있습니다. 앞선 예제 추적 과정을 다시 한번 살펴보세요.)"와 같은 격려 문구만 남길 것.
```

## 4. 전략적 시각화 판단 기준 (Visual Scaffolding Strategy)

시각 자료(Mermaid, 이미지)는 자원이자 비용입니다. 모든 문제에 넣기보다 다음 기준에 따라 **전략적으로 배치**합니다.

### ✅ 시각 자료가 필요한 경우 (MUST)
- **개념의 첫 등장**: 단원에서 가장 처음 접하는 튜토리얼 문제 (예: `ALLv05001`).
- **공간/기하 로직**: 직사각형 자르기, 미로 찾기, 체스판 등 눈으로 봐야 이해되는 문제 (예: `ALLv05010`).
- **복잡한 분기**: 재귀 호출이 여러 갈래로 나뉘어 머릿속 트리가 꼬이는 경우 (예: 피보나치, N-Queen).

### ❌ 시각 자료가 필요 없는 경우 (SKIP)
- **단순 반복/변형**: 이전 문제의 로직을 살짝만 바꾼 경우 (예: 1~N 출력 후 N~1 출력).
- **자가 설명적 출력**: `ALLv05003`(챗봇)처럼 출력 예시 자체가 구조를 충분히 시각적으로 보여주는 경우.
- **산술적 재귀**: 팩토리얼처럼 수식만으로도 충분히 명확한 경우.

> **Tip**: "이 그림이 선생님의 설명을 5분 이상 아껴줄 수 있는가?"를 질문해보세요. 답변이 "YES"라면 추가합니다.

### 💡 일관성을 위한 표준 용어 가이드

* 문제 간의 이질감을 줄이기 위해 다음 용어를 통일하여 사용합니다.
	- `Base Case` → **기저 사례 (멈춤 조건)**
	- `Recursive Step` → **재귀 단계 (나아가는 과정)**
	- `Trace` → **컴퓨터의 생각 과정 따라가기**
	- `Parameter` → **매개변수 (재료)**

## 5. 실제 적용 사례 (Case Studies)

### 📌 Case 1: ALLv05001 — 재귀함수 튜토리얼

**원본 문제 진단 (Prompt A 실행 결과)**

| 항목 | 현재 상태 | 문제점 |
|:---|:---|:---|
| 시각적 증거 ⭐1 | C 코드 스크린샷 3장 | Python/Java 학생은 그림을 봐도 모른다 |
| 예제 추적 ⭐2 | `f(1)이 f(2)를 실행` 정도만 언급 | "왜 1부터 N이 출력되는가"의 추적이 없다 |
| 개념 중립성 ⭐3 | C 이미지 의존 | `printf`를 모르면 이미지 자체가 방해 요소 |
| 점진적 힌트 ⭐4 | `has_hint: "false"` | 힌트 자체가 없음 |
| 실세계 연결 ⭐5 | 없음 | "자기 자신을 부른다"는 말 외에 비유 없음 |

**권장 개선 방향**

1. **언어 중립 개념 섹션 추가**: "재귀는 러시아 인형(마트료시카)과 같습니다. 큰 인형을 열면 똑같이 생긴 작은 인형이 나옵니다." 와 같은 비유를 문제 설명 최상단에 배치.
2. **Mermaid 호출 트리 추가**: `f(1) → f(2) → f(3) → f(4) → f(5) → 종료` 흐름을 시각화.
3. **3단계 힌트 추가**:
   - 힌트1: "함수가 자기 자신을 부를 때, 언제 멈춰야 할까?"
   - 힌트2: "매개변수 n이 목표 N보다 커지면 멈춘다. 멈추기 전에 무엇을 출력해야 할까?"
   - 힌트3: `solve(n) { 출력(n); if n < N → solve(n+1); }`

### 📌 Case 2: ALLv05010 — 직사각형 (GCD 기반 재귀)

**원본 문제 진단 (Prompt A 실행 결과)**

이 문제는 "**3 7 → 왜 5인가?**" 질문이 100% 발생합니다. 학생들은 문제를 다 읽어도 답 도출 방식을 이해하지 못합니다.

| 항목 | 현재 상태 | 문제점 |
|:---|:---|:---|
| 시각적 증거 ⭐1 | 없음 | "잘라내는 과정"을 그림 없이 이해하기 불가능 |
| 예제 추적 ⭐2 | 없음 | `3 7 → 5`가 왜 나오는지 전혀 설명 없음 |
| 개념 중립성 ⭐3 | 양호 | 텍스트 기반이라 언어 독립적 |
| 점진적 힌트 ⭐4 | `has_hint: "false"` | 힌트 없음. 학생 스스로 절단 패턴을 발견해야 함 |
| 실세계 연결 ⭐5 | 없음 | "정훈이가 종이를 자른다"는 설정만 있음 |

**핵심 추가가 필요한 섹션: 단계별 시각적 추적**

```
3 × 7 직사각형을 자르는 과정:

[Step 1] 3 × 7 → 3 × 3 정사각형 하나 잘라냄 → 남은 부분: 3 × 4     (✂️ 1개)
[Step 2] 3 × 4 → 3 × 3 정사각형 하나 잘라냄 → 남은 부분: 3 × 1     (✂️ 1개)
[Step 3] 3 × 1 → 1 × 1 정사각형 하나 잘라냄 → 남은 부분: 2 × 1     (✂️ 1개)
[Step 4] 2 × 1 → 1 × 1 정사각형 하나 잘라냄 → 남은 부분: 1 × 1     (✂️ 1개)
[Step 5] 1 × 1 → 이미 정사각형! 끝.                                   (✂️ 1개)
                                                          ─────────────
                                                          총 5개
```

**권장 개선 방향: 3단계 패턴 발견 힌트**

> 방침: GCD/최대공약수를 직접 언급하지 않는다. 학생이 절단 규칙을 반복 추적하다 보면 스스로 패턴을 발견하도록 유도한다.

- **힌트 1 (방향)**: 종이를 자르고 남은 부분을 다시 들여다봐. 남은 부분도 **직사각형**이야. 그 직사각형에도 똑같은 방법을 쓸 수 있지 않을까? — 같은 문제가 더 작게 반복되는 구조를 느껴보자.
- **힌트 2 (전략)**: N과 M 중 **더 긴 쪽**에서 **더 짧은 쪽**만큼 잘라낸다고 생각해보자. 아래 표를 직접 채워봐.

  | 단계 | 남은 N | 남은 M | 잘라낸 정사각형 수 |
  |:---:|:---:|:---:|:---:|
  | 시작 | 3 | 7 | 0 |
  | 1 | 3 | 4 | 1 |
  | 2 | 3 | 1 | 2 |
  | ... | ... | ... | ... |

  언제 멈추게 될까? N == M이 되는 순간과 연결해봐.

- **힌트 3 (구현 방향)**: N과 M이 같을 때가 기저 사례(base case)야. 그 전까지는 큰 수에서 작은 수를 빼고, 개수를 1씩 더하면 돼.

  ```
  cut(N, M):
    if N == M: return 1
    if N > M:  return 1 + cut(N - M, M)
    else:      return 1 + cut(N, M - N)
  ```
  이 패턴이 익숙하다면? 그냥 계속 빼는 방식을 한 번에 처리하는 방법을 고민해봐. (힌트: 나머지 연산 `%`)

## 6. 작성 및 수정 시 절대 준수 사항 (Mandates)

AI 에이전트가 MD 파일을 수정할 때 반드시 지켜야 할 **형식적 제약**입니다.

1.  **헤더 구조 유지**: 모든 문제 MD는 반드시 `## 1. 문제 설명` / `## 2. 입출력 설명` / `## 3. 예시` / `## 4. 힌트` 의 번호 체계를 사용합니다. 이 구조는 **필수**이며 변경하지 않습니다.
2.  **수정 범위 제한**:
    - **1순위**: `## 1. 문제 설명` 본문 (개념 보완, 시각화 추가)
    - **2순위**: `## 4. 힌트` 본문 (스캐폴딩 재작성)
    - 프론트메터(YAML)는 명확한 수정 요청이 없는 한 손대지 않습니다.
3.  **예제 입출력 보존**: 기존의 예제 입출력 데이터는 논리적 오류가 없는 한 수정하지 않습니다. (추가는 가능)
4.  **예제 추적(Trace) 배치**: 예제 작동 원리 설명은 반드시 `## 4. 힌트` 또는 `## 1. 문제 설명` 내부에 삽입하십시오.
5.  **예시 섹션의 순수성**: `## 3. 예시` 섹션에는 `### 예시 입력 n`과 `### 예시 출력 n` 외의 설명 텍스트를 절대 추가하지 마십시오. (데이터 파이프라인 정합성 유지)
6. **맥락적 통합 (Contextual Integration)**: 새로운 정보(시각화, 힌트)를 넣을 때 기존 본문과 겹치는 내용이 있다면, 기존 내용을 과감히 삭제하고 AI의 정제된 설명으로 대체하십시오.  
7. **언어 중립성 강제**: 본문에 특정 언어(C, Java 등)에 종속적인 단어(printf, 메인문)나 이미지가 있다면, 이를 일반적인 알고리즘 용어로 교체하거나 삭제하십시오.  
8. **브릿지 문장 필수**: 표나 다이어그램을 삽입하기 전, 반드시 앞 문단과 이어지는 자연스러운 도입 문장을 작성하여 `AI가 생성한 티`를 제거하십시오. 
9. **의도적 여백 (Intentional Emptiness)**: 모든 문제에 3단계 힌트가 들어갈 필요는 없습니다. 단순한 문제임에도 구구절절 설명하는 것은 오히려 학습의 재미를 반감시킵니다. **문제의 난이도에 맞춰 힌트의 깊이를 조절**하십시오.

## 7. 예제 입출력 전략 (Example Selection Strategy)

무조건 예제가 많다고 좋은 것이 아닙니다. `ALLv10005`(소 배치하기)와 같이 **전략적 배치**가 필요합니다.

1.  **교육용 예제 (Educational)**: 문제의 로직을 손으로 따라가면 금방 답이 나오는 직관적인 숫자. (예: 7 15 -> 21)
2.  **함정/반례 예제 (Counter-example)**: 학생이 1차원적으로 생각했을 때 틀리기 쉬운 케이스.
    - 예: "홀수면 무조건 된다"고 생각할 때 "한쪽만 짝수여도 안 됨"을 보여주는 예제 (예: 76 51 -> 0)
    - 예: "큰 홀수면 무조건 많이 된다"고 생각할 때 "중간에 짝수가 섞이면 멈춤"을 보여주는 예제 (예: 95 85 -> 1)

> **원칙**: 단순한 문제는 예시 1~2개로 충분합니다. 하지만 예외 처리가 중요한 문제는 반드시 **'논리적 trap'을 꿰뚫는 예시**를 포함하십시오.

```
[ ] ⭐4 점진적 힌트: 3단계 힌트가 존재하며, 정답 코드를 직접 보여주지 않는다.

[ ] 📌 초보자 감사: Prompt A를 실행하여 취약점 리포트를 받고 대부분을 해결했다.
```

## 9. **삭제의 미학 (The Art of Deletion)**

*  AI가 생성한 고품질 설명이 들어갈 때, 기존의 조잡한 구어체(`~해봅시다`,` 정말 정말 정말 많이나옵니다 `등)는 수정이 아니라 **과감히 삭제**하여 전체 문서를 정제된 전문 강사의 어조로 일원화하십시오.
