# Pygame Marp 슬라이드 작성 가이드

## 1. 목적과 적용 범위

이 문서는 `practice/data/content/pygame_marp_course/` 아래에서 교육용 Marp 슬라이드를 작성할 때 지켜야 할 공용 기준을 정리한 운영 가이드다.

적용 범위:

- 각 차시의 `lesson/slide.md`
- 각 차시의 `assets/`
- 공용 테마 `shared/themes/pygame_theme.css`
- 공용 자산 `shared/assets/`
- 공용 재사용 조각 `shared/snippets/`

이 가이드의 목적은 다음과 같다.

- 차시마다 슬라이드 품질과 구조를 일정하게 유지한다.
- 학생이 슬라이드만 보고도 수업의 흐름을 따라갈 수 있게 만든다.
- 강사가 설명하기 쉬운 `top-down` 구조를 표준으로 삼는다.
- lesson01에서 확인한 시행착오를 다음 차시부터 반복하지 않게 한다.

## 2. 폴더 구조와 각 파일의 역할

기본 구조:

```text
pygame_marp_course/
  README.md
  curriculum.md
  marp_slide_guide.md
  shared/
    assets/
    themes/
    snippets/
  lesson01_ship_movement/
    lesson/slide.md
    assets/
    teacher_notes/
  lesson02_meteor_drop/
  lesson03_collision/
  ...
```

파일 역할:

- `README.md`
  - 코스 루트의 운영 원칙과 source of truth를 설명한다.
- `curriculum.md`
  - 차시 목표와 산출물을 거시적으로 정리한다.
- `lessonXX_topic/lesson/slide.md`
  - 각 차시의 핵심 원본이다.
  - 실제 수업 흐름, 설명, 코드, 실습 안내는 이 파일을 기준으로 누적 관리한다.
- `lessonXX_topic/assets/`
  - 해당 차시에만 쓰는 이미지, 다이어그램, 스크린샷을 둔다.
- `shared/themes/pygame_theme.css`
  - 공용 Marp 테마다.
  - 레이아웃, 타이포, 공용 클래스 규칙은 여기에서 관리한다.
- `shared/assets/`
  - 여러 차시에서 반복 사용하는 공용 아이콘, 배경, 프레임을 둔다.
- `shared/snippets/`
  - 여러 차시에서 반복되는 문구, 패턴, 코드 프레임을 재사용할 때 둔다.

배치 원칙:

- 한 차시에서만 쓰는 자료는 해당 차시 `assets/`에 둔다.
- 두 차시 이상에서 반복될 것이 명확할 때만 `shared/`로 올린다.
- HTML/PDF는 source of truth가 아니다. 필요 시 빌드 산출물로만 취급한다.

## 3. 기본 슬라이드 흐름 템플릿

교육용 슬라이드는 기본적으로 아래 흐름을 따른다.

1. 타이틀 슬라이드
2. 목차 또는 이번 시간 전체 지도
3. 오늘 완성할 산출물 소개
4. Part 1
5. Part 1 본문 슬라이드
6. Part 2
7. Part 2 본문 슬라이드
8. Part 3
9. Part 3 본문 슬라이드
10. 완성 체크리스트 또는 실습 시작 안내

권장 예시:

```md
---
marp: true
theme: pygame_theme
paginate: true
---

<!-- _class: slide-title -->

# 1. 우주선 움직이기

오늘은 방향키로 우주선을 움직이는 기능을 완성한다.

---

<!-- _class: slide-section -->

# 목차

**■ 오늘 수업 전체 지도**

<div class="slide-2column ratio-55">
<div>

- 1. 오늘 만들 게임과 핵심 목표
  - 1.1 완성 화면 보기
  - 1.2 오늘 수정할 함수 보기
- 2. 우주선을 움직이는 원리
  - 2.1 화면 좌표계
  - 2.2 키 입력 연결

</div>
<div>

- 2.3 왜 부드럽게 움직이는가
- 3. 화면 밖으로 못 나가게 막기
  - 3.1 버그 확인
  - 3.2 경계 개념 이해
  - 3.3 방어벽 코드 완성

</div>
</div>
```

핵심 규칙:

- 타이틀 다음에는 반드시 목차 또는 전체 지도를 둔다.
- 학생이 오늘 무엇을 완성하는지 초반 3장 안에 반드시 드러나야 한다.
- `slide-part`는 대목차 진입 지점에서만 사용한다.
- 모든 소목차마다 파트 슬라이드를 넣어 슬라이드 수를 불필요하게 늘리지 않는다.

## 4. Top-Down 수업 설계 원칙

이 코스는 무조건 `top-down`으로 진행한다.

의미:

- 학생은 먼저 `오늘 완성할 기능`을 본다.
- 그다음 `이 기능을 이루는 큰 단계`를 본다.
- 그다음 `코드 조각`, `개념`, `주의사항`으로 내려간다.
- 마지막에 `완성 기준`으로 다시 올라온다.

권장 순서:

1. 오늘 완성할 함수/기능을 선언한다.
2. 입력, 처리, 결과를 한 장으로 요약한다.
3. TODO 조립 순서를 보여준다.
4. 개별 개념 슬라이드로 내려간다.
5. 마지막에 체크리스트로 스스로 검산하게 만든다.

lesson01에서 검증된 예:

- `move_ship(keys)`를 초반에 “오늘 완성할 함수”로 먼저 제시했다.
- TODO 1, TODO 2, TODO 3을 바로 코드로 던지지 않고 “조립 순서”로 먼저 보여줬다.
- 마지막에 “왼쪽/오른쪽 이동”, “0~800 경계” 체크리스트를 두어 학생이 스스로 완료 여부를 판단하게 했다.

작성 규칙:

- 개별 코드 줄 설명부터 시작하지 않는다.
- 함수/기능의 역할 설명 없이 TODO부터 보여주지 않는다.
- 학생 산출물은 “이번 시간 끝나면 무엇이 완성되는가”로 표현한다.

좋은 예:

- “오늘은 `move_ship(keys)`를 완성해서 우주선이 좌우로 움직이게 만든다.”
- “이번 시간 목표는 적이 떨어지는 게임의 `spawn_enemy()`를 완성하는 것이다.”

피해야 할 예:

- “오늘은 `if`, `Rect`, `keys`, `global`을 배운다.”
- “일단 TODO 1을 채우고 TODO 2를 채워보자.”

## 5. 한 장의 슬라이드 밀도 기준

한 장의 슬라이드는 `메시지 1개`를 원칙으로 한다.

판정 기준:

- 학생이 3초 안에 “이 장의 요점”을 말할 수 있어야 한다.
- 코드, 개념, 주의, 미션이 한 장에 3개 이상 섞이면 과밀 가능성이 높다.
- 설명 문단이 길어지면 문장 수를 줄이는 것이 먼저다.

권장 밀도:

- 제목 1개
- 서브헤드 1개
- 핵심 본문 2~4문장 또는 불릿 3~5개
- 코드 블록 1개 또는 이미지 1개
- 보조 콜아웃 1개 이내

분리 기준:

- 코드 설명과 실습 지시는 분리한다.
- 버그 증상과 원인 분석은 분리하거나, 적어도 시각적으로 좌우 분할한다.
- 개념 슬라이드와 체크리스트 슬라이드는 분리한다.

lesson01에서 얻은 교훈:

- `코드 + 주의사항 + 실험 미션`이 한 장에 같이 있으면 학생이 읽어야 할지 입력해야 할지 헷갈린다.
- `버그 화면 + 원인 도식`처럼 역할이 다른 시각 자료는 한 장에 둘 수 있지만, 각각의 역할이 분명해야 한다.
- 과밀한 슬라이드는 목차형/파트형 구조로 재배열하면 이해 부담이 줄어든다.

## 6. 코드, 콜아웃, 이미지, 다이어그램 사용 기준

### 6.1 코드 슬라이드

코드는 “정답 공개”보다 “구조 이해”를 우선한다.

원칙:

- 코드는 한 슬라이드에 한 개념군만 담는다.
- 긴 코드 전체를 보여주기보다 필요한 블럭만 발췌한다.
- 학생이 직접 채울 부분은 위치가 보이게 만든다.
- 정답 전체를 한 번에 공개하지 않아도 된다.

권장:

- TODO 위치 강조
- `# TODO 1`, `# TODO 2`, `# TODO 3`처럼 단계가 보이게 작성
- 코드 옆에 한 줄짜리 역할 설명 추가

### 6.2 콜아웃

`.callout`은 “보충 설명” 또는 “강조 포인트”에만 쓴다.

권장 용도:

- 핵심 개념 한 줄 요약
- 실수하기 쉬운 포인트
- 기억해야 할 규칙

금지:

- 본문보다 더 긴 설명을 콜아웃에 넣지 않는다.
- 모든 슬라이드마다 콜아웃을 붙이지 않는다.
- 콜아웃이 본문을 압도할 정도로 커지게 두지 않는다.

색상 규칙:

- `.callout.tip` : 원리 설명, 이해 포인트
- `.callout.warn` : 실수 주의, 경계 조건, 오타 주의
- `.callout.ok` : 완료 조건, 잘 된 상태, 체크 포인트

### 6.3 이미지

이미지는 “결과를 보여주는 자료”에 우선 사용한다.

권장 용도:

- 완성 화면
- 버그가 발생한 실제 화면
- 배경 스토리 또는 분위기 도입

주의:

- 결과 스크린샷만으로 개념 설명을 대신하지 않는다.
- 증상 스크린샷은 원인 도식과 역할이 다르다.

### 6.4 다이어그램

다이어그램은 “개념을 이해시키는 자료”에 우선 사용한다.

우선 적용 대상:

- 좌표계
- 함수 구조
- TODO 진행 단계
- 충돌 범위
- 경계 조건
- `Rect.left / Rect.right` 같은 속성 개념

lesson01 기준으로 특히 다이어그램이 유효했던 위치:

- `move_ship(keys)`의 입력 → 처리 → 결과
- TODO 1/2/3 조립 순서
- `ship_rect.left / ship_rect.right`
- `0 ~ 800` 경계 제한
- `x` 값이 계속 증가해서 화면 밖으로 나가는 원인

역할 분리 원칙:

- 결과 이미지: “무엇이 만들어지는가”
- 개념 다이어그램: “왜 그렇게 되는가”
- 증상 스크린샷: “무슨 문제가 발생했는가”

## 7. `pygame_theme.css`와 `_class` 사용 규칙

이 코스의 슬라이드는 Marp 고유의 `section` 구조와 `<!-- _class: ... -->`를 중심으로 설계한다.

핵심 원칙:

- 슬라이드 루트는 직접 `<section>`을 쓰지 않는다.
- 슬라이드 전환은 `<!-- _class: ... -->`로 제어한다.
- 공용 레이아웃은 `shared/themes/pygame_theme.css`에 모은다.

기본 인터페이스:

```md
<!-- _class: slide-title -->
<!-- _class: slide-section -->
<!-- _class: slide-part -->
```

공용 레이아웃 클래스:

```html
<div class="slide-2column ratio-64">...</div>
<div class="slide-2column ratio-55">...</div>
<div class="slide-2column ratio-46">...</div>
```

공용 콜아웃 클래스:

```html
<div class="callout tip">...</div>
<div class="callout warn">...</div>
<div class="callout ok">...</div>
```

사용 시점:

- `slide-title`
  - 차시 시작
- `slide-section`
  - 일반 설명 슬라이드
- `slide-part`
  - 대목차 전환
- `.slide-2column`
  - 텍스트와 이미지, 코드와 설명, 버그와 원인처럼 역할이 다른 두 블록을 나눌 때
- `.callout`
  - 보조 설명, 강조 규칙, 실수 주의

금지:

- 슬라이드 루트 패딩을 마크다운 내부 HTML로 다시 만들지 않는다.
- flex 비율을 슬라이드마다 제멋대로 덮어쓰지 않는다.
- 한 슬라이드에 복잡한 중첩 그리드를 남발하지 않는다.

## 8. lesson01에서 얻은 좋은 예 / 피해야 할 예

### 좋은 예

#### 8.1 목차를 초반에 둔 것

- 타이틀 다음에 “이번 시간 전체 지도”를 두면 학생이 현재 위치를 추적하기 쉽다.
- 대목차와 소목차를 미리 보여주면 긴 수업도 안정적으로 따라온다.

#### 8.2 학생 산출물을 초반에 선언한 것

- `move_ship(keys)`를 “오늘 완성할 함수”로 먼저 보여주면 학생이 이후 모든 설명을 같은 목표 아래에서 받아들일 수 있다.

#### 8.3 TODO 조립 순서를 따로 뺀 것

- 개별 코드 조각만 보여줄 때보다, 먼저 조립 순서를 보여주면 학생이 `어디서부터 손을 대야 하는지`를 안다.

#### 8.4 `ship_rect.left/right`, `0~800 경계`를 다이어그램으로 푼 것

- 이 개념은 텍스트 설명보다 도식이 훨씬 빠르다.
- 코드만 보여주면 조건문을 외우지만, 도식이 있으면 이유를 이해한다.

### 피해야 할 예

#### 8.5 한 장에 설명과 실습 지시를 모두 넣는 것

- 설명 문장, 오타 주의, 중간 점검 미션이 한 장에 같이 있으면 학생이 무엇에 집중해야 할지 흐려진다.

#### 8.6 콜아웃을 본문보다 크게 만드는 것

- 콜아웃은 보조 요소다.
- 카드가 본문보다 시각적으로 더 크면 오히려 정보 구조가 흐려진다.

#### 8.7 제목 위치가 슬라이드마다 다르게 보이게 만드는 것

- 본문 슬라이드의 `h1` 시작점은 공통 리듬을 유지해야 한다.
- 제목 다음 첫 블록의 간격까지 같이 관리해야 “고정된 제목”처럼 보인다.

#### 8.8 결과 이미지 하나로 원리까지 설명하려는 것

- 결과 스크린샷은 동기 부여에는 좋지만, 개념 도식의 역할을 대신하지 못한다.

## 9. 작성 전 체크리스트

슬라이드를 쓰기 전에 아래를 먼저 정리한다.

- 이번 차시의 학생 산출물은 무엇인가
- 학생이 수업 끝에 완성해야 할 함수 또는 기능은 무엇인가
- 이번 차시를 3개 안팎의 대목차로 나눌 수 있는가
- 각 대목차 아래 소목차를 행동형 문장으로 표현할 수 있는가
- 결과 이미지, 개념 다이어그램, 증상 스크린샷 중 무엇이 필요한가
- lesson 전용 자료와 shared 자료를 구분했는가

---

## 10. 작성 후 체크리스트

슬라이드 초안을 다 쓴 뒤 아래를 점검한다.

### 구조

- 타이틀 다음에 목차 또는 전체 지도가 있는가
- 오늘 완성할 산출물이 초반 3장 안에 나오는가
- `slide-part`가 대목차 전환에만 사용되는가
- 마지막에 체크리스트 또는 실습 시작 안내가 있는가

### 밀도

- 각 슬라이드가 메시지 1개만 말하는가
- 설명 슬라이드와 실습 슬라이드가 섞여 있지 않은가
- 한 장에 코드, 경고, 미션, 이론을 과하게 몰아넣지 않았는가

### 시각 자료

- 결과 이미지는 “결과”만 담당하는가
- 다이어그램은 “개념”을 설명하는가
- 버그 스크린샷은 증상을, 도식은 원인을 설명하는가
- 이미지 없이도 되는 곳에 억지로 이미지를 넣지 않았는가

### 작성 규칙

- `pygame_theme.css`의 공용 클래스만 사용했는가
- 슬라이드 루트에 직접 `<section>`을 쓰지 않았는가
- lesson 전용 자료가 `shared/`로 잘못 올라가지 않았는가
- 경로가 실제 폴더 구조와 맞는가

### 학생 관점

- 학생이 3초 안에 “오늘 무엇을 완성하는지” 말할 수 있는가
- 학생이 TODO를 어떤 순서로 채울지 알 수 있는가
- 학생이 실행 후 무엇을 확인해야 하는지 스스로 판단할 수 있는가

## 11. 빠른 시작 템플릿

새 차시를 만들 때는 아래 뼈대에서 시작한다.

```md
---
marp: true
theme: pygame_theme
paginate: true
---

<!-- _class: slide-title -->

# N. 차시 제목

한 줄 목표 문장

---

<!-- _class: slide-section -->

# 목차

**■ 오늘 수업 전체 지도**

- 1. 첫 번째 대목차
- 2. 두 번째 대목차
- 3. 세 번째 대목차

---

<!-- _class: slide-section -->

# 오늘 완성할 함수 한눈에 보기

- 입력:
- 처리:
- 결과:

---

<!-- _class: slide-part -->

# 1. 첫 번째 대목차

---

<!-- _class: slide-section -->

# 본문 슬라이드 제목

핵심 설명

---

<!-- _class: slide-section -->

# 완성 체크리스트

- 기능이 기대대로 동작하는가
- 경계 조건이 맞는가
- TODO가 모두 사라졌는가
```

이 템플릿은 시작점일 뿐이다. 실제 차시에서는 대목차 수, 다이어그램 수, 코드 슬라이드 수를 차시 목표에 맞게 조정한다.
